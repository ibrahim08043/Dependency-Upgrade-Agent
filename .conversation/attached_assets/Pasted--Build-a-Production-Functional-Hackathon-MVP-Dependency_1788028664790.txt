# Build a Production-Functional Hackathon MVP: Dependency Major-Version Upgrade Agent

## 1. PROJECT GOAL

Build a fully working web application called:

**Dependency Major-Version Upgrade Agent**

The application is an AI-powered software engineering agent that takes an existing JavaScript/TypeScript repository and autonomously migrates a selected dependency from one major version to another.

This is NOT a mock/demo UI.

Every major feature shown in the UI must actually work.

Do NOT create fake progress bars, fake test results, fake AI responses, fake patches, fake repository analysis, hardcoded migration results, or placeholder buttons.

The system must perform real repository analysis, real AI reasoning through the Grok/xAI API, real file modifications in a temporary workspace, real test/build execution, real failure analysis, and real retry attempts.

---

# 2. HACKATHON MVP SCOPE

For the first working version, support:

* JavaScript
* TypeScript
* npm
* pnpm
* Git repositories / uploaded ZIP repositories
* Dependency major-version migrations

Do NOT attempt to support every programming language or package manager.

The MVP should focus on making one ecosystem extremely reliable.

Primary target:

**JavaScript/TypeScript + npm/pnpm**

Example migration:

* React 18 → React 19
* ESLint major-version migration
* Axios major-version migration
* another real dependency major-version migration

The architecture should be extensible so additional ecosystems can be added later.

---

# 3. IMPORTANT PRODUCT PRINCIPLE

The application must behave like an actual coding agent.

Do NOT simply send:

"Upgrade this dependency"

to an LLM and then display its answer.

Instead, implement a real agentic workflow:

Repository
→ Analyze
→ Understand dependency
→ Research migration information
→ Find affected code
→ Plan migration
→ Modify code
→ Run tests
→ Run build/typecheck
→ Analyze failures
→ Fix failures
→ Retry
→ Verify
→ Generate final report
→ Show actual diff

The application must be able to recover from failures.

---

# 4. AI PROVIDER

Use the **Grok/xAI API** as the primary LLM provider.

Environment variable:

```env
XAI_API_KEY=your_xai_api_key
```

Never hardcode the API key.

Use the official xAI API/SDK or standard HTTPS API calls.

Create a clean AI provider abstraction so another LLM can be added later without rewriting the application.

For example:

```text
AIProvider
    └── GrokProvider
```

The Grok provider should support:

* structured prompts
* tool/function calling if supported by the selected API
* migration planning
* code analysis
* failure diagnosis
* patch generation
* verification reasoning

The backend must gracefully report an API configuration error if `XAI_API_KEY` is missing.

Do NOT silently fall back to fake responses.

# 5. OPTIONAL GITHUB API

Support two repository input methods:

### Method A — ZIP upload

This must work without GitHub credentials.

User uploads a `.zip`.

The backend extracts it into a temporary workspace.

### Method B — GitHub repository URL

Allow the user to enter a GitHub repository URL.

Use:

```env
GITHUB_TOKEN=optional_github_token
```

The token should be optional.

Public repositories should work without the token whenever possible.

Private repositories require the token.

Do not expose the GitHub token to the browser.

# 7. SECURITY REQUIREMENTS

This application executes code from repositories.

Treat repository code as untrusted.

Never execute uploaded repository code directly against the application's own source tree.

Every migration must happen inside a temporary workspace.

Use:

```text
/tmp/dependency-agent/<unique-job-id>/
```

or an equivalent isolated workspace.

Set command timeouts.

Prevent infinite processes.

Limit:

* execution time
* output size
* retry count
* workspace size where practical

Never expose:

* XAI API key
* GitHub token
* server environment variables

to the frontend.

Do not allow arbitrary server-side file paths from user input.

Validate uploaded ZIP files.

Prevent ZIP path traversal attacks.

# 21. SELF-HEALING LOOP

This is the signature feature of the application.

Workflow:

```text
Migration
    ↓
Run tests
    ↓
PASS ───────────────→ Verification
    │
    FAIL
    ↓
Analyze error with Grok
    ↓
Inspect affected files
    ↓
Generate corrective patch
    ↓
Apply patch
    ↓
Run tests again
    ↓

FAIL → retry
```

Maximum retries:

```text

```

Do not create an infinite loop.

For every retry store:

```text

failure
diagnosis
files changed
commands executed
result
```
